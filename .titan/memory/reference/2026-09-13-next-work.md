# Next implementation block

Date: 2026-09-13
Status: pending
Source: Phase 4 of `.titan/plans/prp-vision-studio-mvp.md` and confirmed product rules in `BUSINESS_LOGIC.md`.

## Objective

Finish Phase 4 with an individual daily cashbox for each seller, branch and
currency. Closing a cashbox must preserve an immutable accounting snapshot while
allowing later payments to be received and included in a complementary closure.

## Required behavior

1. Add seller cashboxes and closure records scoped by organization, branch,
   seller, business date and currency.
2. Create one primary closure per seller/date/currency. Store expected amount,
   declared amount, difference, actor and timestamp as immutable values.
3. Closing must not block later payments. A payment received after the primary
   closure is marked as post-close and remains linked to its receiving seller.
4. Add sequential complementary closures that include only unclosed post-close
   payments. They never modify or replace the primary closure.
5. Provide a consolidated daily summary equal to the primary closure plus all
   complementary closures, preserving separate currency totals.
6. Sellers can access only their own cashbox. Owners can review organization data
   with branch/seller/date filters. External providers and unrelated tenants have
   no access.
7. Expired or suspended organizations remain read-only. Payments and closures are
   never physically deleted or edited.

## Implementation order

1. Database tables, constraints, indexes and tenant/seller RLS.
2. Atomic primary and complementary closure functions with concurrent-payment
   locking and deterministic allocation.
3. Update payment insertion so `is_post_close` is assigned by the database from
   the latest applicable primary closure, never trusted from the client.
4. Remote rollback fixtures for exact totals, differences, late payments,
   complementary sequencing, immutability and seller/tenant isolation.
5. Add the `/cashbox` seller workspace and owner review using the existing Caribe
   moderno design patterns.
6. Run TypeScript, ESLint, production build, Supabase advisors and responsive QA
   when browser automation is available.

## Acceptance criteria

- A primary closure captures every eligible payment exactly once.
- A later payment succeeds and is visibly marked post-close.
- A complementary closure captures that later payment without altering the
  primary closure.
- Repeating a closure cannot double-count payments.
- Expected, declared and difference amounts are exact numeric values per currency.
- Closure rows and their payment allocations reject update/delete operations.
- Seller, owner, unrelated seller and unrelated tenant access fixtures pass.

After this block, Phase 4 is complete and the next phase is production/provider
workflows and incidents.
